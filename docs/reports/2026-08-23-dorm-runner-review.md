# 宿舍常驻 runner 与现网 Broker 耦合复核

复核日期：2026-08-23
复核基线：`d4d5308bcb67a9000397add9d8688d50beba0245`
复核对象：`docs/reports/2026-08-22-dorm-runner-rfc.md`

## 结论

RFC 的主方向合理：4B 保持唯一队列，宿舍 runner 只承担受控执行，能够避免双 Broker 带来的 claim、重试和状态合并问题。现阶段不应购买硬件，也不应提前扩展任务卡；先用现有笔记本和组内资源验证是否真的存在“任务因设备不能常驻而长期阻塞”的问题。

六个问题的结论如下。

| 问题 | 结论 | 建议 |
|---|---|---|
| 4B 单队列还是 runner 再跑 Broker | 同意 4B 单队列 | runner 只执行，不保存调度真相 |
| P0 禁止 GPU 注入是否太软 | 人工约定偏软，但关键词拦截不是正确硬闸 | P0 不给 4B 配 runner 密钥、目标和远程执行入口 |
| 新字段如何设计 | 倾向独立远程执行器 | 使用受控目标别名，不允许任务卡填写主机名或命令前缀 |
| 12G 常驻是否值得 | 有可用性价值，没有能力升级 | 只有常驻性已成为实测瓶颈时才值得买 |
| 产物由谁回传 | 由 4B 主动拉取 | 先拉到暂存目录，校验后再发布到 attempt 目录 |
| 是否偏离论文目标 | 当前继续购置会偏离 | 默认采用 0 元方案，以任务阻塞记录触发采购评估 |

## 单一队列

4B 继续拥有任务状态是当前约束下最简单且最稳妥的设计。`orchestra/broker/db.py` 以单个 SQLite 数据库保存 `queued/running/done/failed/blocked/invalid`，`claim_task()` 通过条件更新完成单点 claim；`orchestra/broker/dispatcher.py` 又在同一进程内处理重试、依赖阻塞和崩溃恢复。若 runner 再运行一套 Broker，就必须新增跨节点租约、状态合并和脑裂恢复，复杂度明显超过收益。

runner 应被视为一种有生命周期的外部进程，而不是第二个调度节点。4B 决定 attempt 编号、任务状态和最终产物是否有效；runner 只接收一个不可变任务包，返回退出状态和产物包。runner 离线时任务失败或等待，雷达和其他本地任务不受影响。

这一结论有一个前提：4B 自身仍是单实例运行。当前 SQLite claim 能防止同一数据库上的重复领取，但没有跨主机租约；因此不能通过共享目录让第二个 dispatcher 指向同一数据库。

## P0 能力隔离

依靠任务正文里写“目标机”只能表达意图，不能形成技术边界。不过，在 runner 尚未接入时，搜索 `nvidia-smi`、`docker` 或 `ssh` 并将任务判 invalid 也不合适：

- shell 文本可以通过脚本、变量或间接命令轻易绕过。
- 运维和环境探测可能合法使用这些词，关键词门会产生误伤。
- 当前真正需要防止的是 4B 获得远程执行能力，而不是识别任务正文的研究主题。

P0 最低成本且可验证的硬闸是能力隔离：

1. 4B 不保存宿舍 runner 的私钥或可用 SSH 身份。
2. Broker 配置中不存在 runner 目标。
3. 任务卡白名单继续只允许现有执行器。
4. 4B 不安装面向 runner 的调度脚本或 systemd 单元。

满足这四点时，即使任务正文表达了 GPU 意图，也无法从 Broker 获得远程执行能力。现有 `taskfile.py` 会拒绝未知字段，这已经是有效的一层边界。

## 字段与配置

`executor: shell` 加 `runtime: dorm` 会让 shell 执行器同时承担本地进程和远程生命周期，后续在超时、取消、回传和错误分类上不断出现条件分支。独立的远程执行器更符合现有结构，因为 `executor.py` 已按执行器类型选择完全不同的启动方式。

建议 P1 采用以下语义，而不是允许任务卡填写原始主机：

```yaml
executor: remote
target: dorm
```

`target` 只能是 Broker 配置中预注册的别名。主机地址、SSH 用户、密钥路径、远程工作根目录和允许的容器入口全部保存在 Broker 本地配置中，任务卡不能覆盖。若 P1 只有一台 runner，也可以先省略 `target`，由 `remote` 执行器绑定唯一配置，等出现第二台真实目标后再增加字段。

字段扩展必须等本机与 4B 的解析器版本一致后再做。当前仓库的 `taskfile.py` 已拒绝未知字段、重复 key、越界 timeout 和非法模型值，而 README 明确记录 4B 尚未部署这一版本。在分叉消失前增加字段，会使同一任务卡在两端产生不同结果。

## 12G 常驻价值

12GB 常驻 runner 提升的是时间可用性，不是可运行模型的上限。它仍可能有价值：长任务可以在人离开后继续、环境可以固定在 Docker 镜像中、笔记本不必长期插电。但这些收益只有在“常驻性”已经阻塞实验时成立。

采购前应先保留一个月的任务记录，至少包含：

- 因笔记本离线而推迟或中断的任务数量。
- 这些任务的预计运行时长和显存峰值。
- 改用组内服务器的等待时间。
- 任务中有多少确实能在 12GB 显存完成。

若主要问题是显存不足，另一台 12GB 机器不会解决问题；若主要问题是任务需要过夜运行，低价无卡塔式主机也只有在后续显卡来源明确时才有意义。当前证据不足以支持购买，0 元方案应是默认选择。

## 产物回传

4B 主动拉取比 runner 反向写入 Broker 数据目录更清晰。反向 `scp` 要让 runner 持有写入队列主机的凭据，而且 runner 可以直接制造或覆盖 attempt 内容；一旦传输中断，Broker 很难判断目录是部分产物还是完整结果。

推荐的 P1 协议是：

1. 4B 在 claim 后分配 task ID、attempt 编号和一次性运行标识。
2. runner 在自己的 `/data/jobs/<task>/<attempt>/<run-id>/` 中执行。
3. runner 完成后生成清单，记录文件相对路径、大小和 SHA-256。
4. 4B 将产物拉到 Broker 上的临时目录，例如 `attempt-N.incoming-<run-id>`。
5. 4B 校验清单、必需产物和 `metrics.json` 后，将临时目录发布为正式 attempt。
6. `state.json` 最后写入；只有发布完成后，数据库状态才能变为 `done`。

当前 `executor.py` 会先建立 `attempt-N`，随后在其中增量写文件；这个语义适合本地进程，但不能直接照搬到跨机传输。远程执行需要显式区分“远端运行完成”“传输完成”“产物校验完成”三个阶段，否则网络中断会留下看似存在但不完整的 attempt。

## 失败与重试

RFC 对远程失败语义记录不足，这是进入 P1 前必须补齐的部分。

### 断连与超时

当前本地执行器超时后可以终止进程组。远程 SSH 进程被杀并不等于远端容器被杀；网络断开后，任务可能继续占用 GPU。远程执行必须返回稳定的远端 job ID，并提供独立的查询和取消命令。Broker 只有确认远端任务已停止，或经过人工处置，才能安全重试。

### 重复执行

`db.py` 在 Broker 重启后会把所有 `running` 改为 `failed`，下一轮可能重试。对本地任务这是可接受的，对远程任务可能造成旧容器仍运行、新 attempt 又启动。runner 必须按 `run-id` 幂等创建任务，并允许 Broker 重连后查询原任务，而不是直接启动副本。

### 错误分类

至少应区分：

- runner 不可达。
- 任务启动失败。
- 任务非零退出。
- Broker 超时但远端状态未知。
- 远端取消成功或失败。
- 产物传输失败。
- 产物校验失败。

这些错误不能全部压成普通 `failed` 后直接自动重试。尤其是“远端状态未知”，应阻止自动创建下一次执行。

## 安全边界

RFC 已提出低权限用户、命令白名单和默认断外网，但还缺少以下约束：

- 固定 runner 主机密钥，连接时拒绝主机指纹漂移。
- 为 Broker 单独创建 SSH 密钥，不复用人工登录密钥。
- runner 的 `authorized_keys` 使用强制命令，禁止任意 shell、端口转发和 agent 转发。
- Docker 镜像使用不可变 digest，不使用浮动 tag。
- 容器默认无特权、只读根文件系统、限制 CPU、内存、磁盘和运行时长。
- 数据集目录与产物目录分离，明确保留期限和清理责任。
- 默认网络策略应允许 4B 与 runner 之间的 Tailscale 通信，同时阻断任务容器的非必要外网；不能把“主机完全断网”和“任务容器断外网”混为一件事。

“只允许 `docker run`”仍然过宽，因为挂载宿主目录、特权模式和设备参数都可能扩大权限。更稳妥的入口是 runner 上固定的包装命令，Broker 只提交经过校验的任务包和有限参数。

## 采购边界

当前阶段继续购置设备会增加维护面，但尚无任务阻塞数据证明收益。建议保持 0 元方案，只有同时满足以下条件时才重新评估：

- 连续出现多次可在单卡完成、但因笔记本不能常驻而延误的实验。
- 组内资源等待时间已经影响明确的论文节点。
- 已用现有机器手动跑通至少 2–3 个真实实验，并证明容器、数据和产物契约可复用。
- 预期工作负载的显存和运行时分布已经记录，而不是按单个模型猜测。

如果最终购买，决策应先回答需要的是“常驻时间”还是“更大显存”。前者可以接受同档 GPU，后者必须提高显存档位；两种需求不应混在同一个预算理由中。

## 已发现的漏账

### 现网数据根不一致

README 表述 `sync_push` 和 `sync_pull` 默认使用 `/home/liuxfs/broker-data`，但仓库中的 `orchestra/scripts/sync_push.sh` 仍默认 `/mnt/broker`；`sync_pull.sh` 才使用现网目录。`orchestra/broker/config.example.json` 和若干维护脚本也仍以 `/mnt/broker` 为默认值。

这会导致未显式设置 `ORCHESTRA_REMOTE_ROOT` 时，任务推送与结果拉取指向不同目录。该问题与宿舍 runner 无关，但会直接影响 P0 任务入口，优先级高于扩展远程执行器。本次按复核要求只记录，不修改代码。

### P1 验收不足

“手动跑通 2–3 篇”只能证明正常路径，不能证明调度语义。P1 进入 Broker 前还应人工演练：

- SSH 在运行中断开。
- Broker 在远端任务运行时重启。
- runner 在运行中重启。
- 产物传输到一半中断。
- 远端任务超时但取消失败。
- 同一个 run ID 被重复提交。
- 磁盘不足和产物超出配额。

每次演练都应回答远端是否仍在运行、Broker 是否会重复启动、attempt 是否可识别为完整、人工如何恢复。

### 状态模型不足

当前数据库只有一个 `status` 和一段 `error`，没有远端 job ID、run ID、心跳、取消状态或产物传输状态。P1 如果直接接入，会把远程任务的多个阶段压缩成 `running/failed/done`，无法可靠恢复。远程执行器设计应先定义状态和恢复规则，再决定代码形态。

### 路径兼容债务

模型 patch、历史任务卡、备份和维护脚本中仍存在 `/mnt/broker` 绝对路径。只修改远程执行器不会解决这些路径分叉。进入 P1 前应先确认 4B 的实际配置和脚本统一使用同一数据根，并用仓库内检查记录结果。

## 其他两项复核

### 本机与 4B 解析器分叉

应在下一次部署窗口一次性对齐，并在部署后用合法任务卡和包含未知字段的非法任务卡各做一次验证。合法卡应进入队列，非法卡应归档为 `.bad`；同时确认雷达模板仍能解析。对齐前不增加任何新字段。

### digest 暂不锁定

当前 `academic-shared` 是 required skill，`expected_digest` 为 `null`。`check_skills.py --strict` 会因此返回非零，薄门禁会报告整体失败。暂不锁定是可接受的人工审阅状态，但不能把它描述为系统可正常 ingest 的状态；在锁定前，真实实验入账应继续 HARD。

## 建议顺序

1. 先消除现网数据根和本机、4B 解析器分叉。
2. 保持 P0 能力隔离，不增加远程字段或凭据。
3. 用现有机器手动验证真实实验与容器产物契约，同时记录任务阻塞证据。
4. 只有常驻需求被证实后，再决定是否购买 runner。
5. P1 先写远程生命周期、幂等、取消和产物发布协议，再扩展任务字段。
