# Stage S6.5: Reproducibility Check [Strategist]

**Gate:** Q6.5 (SOFT BLOCK) — reproducibility check complete: data backed up, code documented, seeds set, DAS drafted
**Goal:** Verify that another researcher with your data could reproduce your results. Self-audit that catches the most common causes of irreproducible papers before submission.
**Needs Composers:** none

## Decisions

### Composer Sequence

1. Run Data Availability Self-Check (S6.5A)
2. Run Code Self-Check (S6.5B)
3. Document Random Seeds & Stochastic Reproducibility (S6.5C)
4. Handle Failure Recovery (S6.5D)
5. CS Artifact Evaluation — conditional (S6.5-CS)

### Data Availability Self-Check (S6.5, lines 9-15)

Four-question checklist. Per-entry routing:

| # | Question | Yes Route | No Route (Action Required) |
|---|----------|-----------|---------------------------|
| 1 | Is the raw data backed up to a non-local location? | Safe. Proceed. | Back up before submission. |
| 2 | Can someone else legally access this data? | Proceed. | Document access restrictions in Data Availability Statement. |
| 3 | Is the data version/dataset/date explicitly recorded? | Cite in paper. | Add: "Data accessed from [source] on [date], version [X]." |
| 4 | Are exclusion criteria and cleaning steps fully documented? | Include in supplement. | Write the cleaning pipeline step-by-step. |

### Code Self-Check (S6.5, lines 17-24)

| # | Question | Yes Route | No Route (Action Required) |
|---|----------|-----------|---------------------------|
| 1 | Can you regenerate all tables/figures with one script? | Ready. | Consolidate into a single run script. |
| 2 | Are all package versions recorded? | Good. | Run `pip freeze > requirements.txt` or equivalent. |
| 3 | Can you share code without embarrassment? | Ship it. | Clean up dead ends, hardcoded paths, credential leakage. |
| 4 | Does the code run on a different machine? | Confident. | Test on colleague's machine or fresh environment. |

### Random Seed & Stochastic Reproducibility (S6.5, lines 26-33)

Document for each analysis step:

| Element | What to Record |
|---------|---------------|
| Random seed | "Set seed: 20240115 for main analysis, 20240116 for sensitivity" |
| Software version | "R 4.3.2, lme4 1.1-35.1" |
| OS / architecture | "Ubuntu 22.04 x86_64" or "macOS 14.1 ARM" |
| Non-deterministic algorithms | "MCMC chains, 4 chains × 10,000 iterations, seed 42" |

### Failure Recovery Routing (S6.5, lines 35-42)

| Failure Mode | Recovery Action |
|-------------|----------------|
| "I ran it again and got different numbers" | Missing seed or non-deterministic algorithm. Set seed, document algorithm version. |
| "The code doesn't run from scratch" | Dependency drift or execution order. Build from fresh environment, fix order. |
| "I can't remember how I got this result" | Add README with: input data → script → output mapping. |
| "A variable is defined but I forgot where it came from" | Add data dictionary to supplement. |

### CS Artifact Evaluation (S6.5, lines 56-74) — Conditional, CS/Engineering Only

IF paper targets CS conferences (ICSE, PLDI, OSDI, NeurIPS D&B, etc.) or journals (JOSS, SoftwareX):

| Check | Requirement |
|-------|------------|
| **Anonymized repository** | For double-blind: no author names, institution URLs, identifying comments. Use anonymous GitHub/Zenodo. |
| **Environment** | Dockerfile or VM image reproducing exact runtime. |
| **One-command reproduction** | Single script regenerates all results. `./reproduce.sh` or `make reproduce`. |
| **CI badge** | Green CI badge on anonymous repo proves pipeline runs. |
| **Post-acceptance plan** | Note which repo is anonymous (review) vs. public (post-acceptance). DO NOT mix. |

Document which badge level is targeted:
- **Available:** code/data in permanent repository (DOI)
- **Evaluated:** artifacts documented and complete
- **Reproduced:** main results independently regenerated

Artifact appendix must map each paper claim to the script + seed that produces the evidence.

### Gate Nature (S6.5, lines 46-54)

Q6.5 is a **SOFT BLOCK** — not a hard submission blocker.

- IF most items are unchecked → paper may still be submitted, but cannot be verified
  - Some journals desk-reject on apparent irreproducibility
  - Fix what you can, document the rest as limitations
- This is an advisory self-audit, not a formal submission requirement

### STOP-AND-ASK Points
- Data not backed up → remind user to back up before submission
- Code doesn't run on different machine → advise testing in fresh environment
- CS artifact evaluation not configured → ask if targeting artifact evaluation badges

## Gate

### Q6.5 Gate Checklist
- [ ] Raw data is backed up and version identified
- [ ] One-script regeneration of all results works
- [ ] Package/environment versions recorded
- [ ] Random seeds documented
- [ ] Data Availability Statement drafted (or confident about access path)

### Gate Failure Route
Q6.5 is SOFT BLOCK.

1. First failure → identify which check items failed → route back to corresponding sub-step for repair → re-run → re-evaluate.
2. Most items unchecked → this does NOT block submission, but document limitations in the manuscript.
3. For CS papers: IF artifact evaluation not prepared → route to S6.5-CS (Artifact Evaluation) for Dockerfile, anonymization, and CI badge setup.
